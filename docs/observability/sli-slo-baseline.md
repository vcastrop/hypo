# MyBookstore – SLIs, SLOs and Steady-State Baseline

## 1. Purpose

This document defines the initial Service Level Indicators (SLIs), Service Level Objectives (SLOs), and steady-state baseline used to evaluate the resilience of the MyBookstore demo application before controlled chaos experiments.

The baseline represents the observed normal behavior of the monitored path under a controlled workload and without active chaos experiments. It provides a reference for later before/during/after comparisons and PASS/FAIL evaluations.

## 2. Scope

The current application-level observability scope is the `catalog-service`, specifically the HTTP path exercised through the API Gateway to `/api/books`.

This baseline must not be interpreted as an application-wide SLO for every MyBookstore microservice. At this stage, `catalog-service` is the service exposing the application-level Prometheus request metrics used for the baseline.

Prometheus discovers each `catalog-service` pod independently, allowing both replicas to be observed without mixing process-local counters behind a single Kubernetes Service target.

## 3. Test Environment

The baseline was measured in the local development environment under the following conditions:

| Parameter | Configuration |

| Control-plane nodes | 1 |

The workload was generated by the project's Traffic Generator using one active simulation. No chaos experiment was active during the measurement.

## 4. Instrumentation

`catalog-service` exposes Prometheus metrics at `/metrics`.

The service defines the following application-level metrics:

- `http_requests_total`: counter of HTTP requests, labeled by HTTP method and status code.
- `http_request_duration_seconds`: histogram of HTTP request duration, labeled by HTTP method and status code.

The configured duration histogram buckets are:

`0.05, 0.1, 0.3, 0.5, 1, 2 seconds`

The service also exposes the default Node.js process metrics collected by `prom-client`, including CPU and resident memory metrics.

Prometheus uses Kubernetes pod discovery in the `mybookstore` namespace and keeps the HTTP port `5001` of pods labeled `app=catalog-service`. Each discovered target receives a `pod` label so replicas can be evaluated independently.

## 5. Service Level Indicators

### 5.1 Target Availability

**Purpose:** determine whether all expected Catalog replicas are reachable by Prometheus.

```promql
sum(up{job="catalog-service"}) / count(up{job="catalog-service"}) * 100
```

The `up` metric represents Prometheus target/scrape availability. It should not be confused with HTTP request success rate.

### 5.2 Request Success Rate

**Purpose:** measure the percentage of requests completed with successful HTTP status codes.

```promql
100 *
sum(rate(http_requests_total{job="catalog-service",status=~"2..|3.."}[5m]))
/
sum(rate(http_requests_total{job="catalog-service"}[5m]))
```

### 5.3 Request Error Rate

**Purpose:** measure the percentage of requests returning HTTP 4xx or 5xx status codes.

```promql
100 *
(
  sum(rate(http_requests_total{job="catalog-service",status=~"4..|5.."}[5m]))
  or vector(0)
)
/
sum(rate(http_requests_total{job="catalog-service"}[5m]))
```

### 5.4 P95 Request Latency

**Purpose:** estimate the request duration below which 95% of observed requests fall.

```promql
histogram_quantile(
  0.95,
  sum(rate(http_request_duration_seconds_bucket{job="catalog-service"}[5m])) by (le)
)
```

### 5.5 Throughput

**Purpose:** characterize the workload under which the baseline and SLOs are evaluated.

```promql
sum(rate(http_requests_total{job="catalog-service"}[5m]))
```

Throughput is treated as a workload condition rather than a service-level objective.

## 6. Operational Indicators

CPU and memory are recorded as supporting operational indicators. They help identify resource changes during chaos experiments but are not currently treated as user-facing SLOs.

### CPU

```promql
sum(rate(process_cpu_seconds_total{job="catalog-service"}[5m]))
```

### Resident Memory

```promql
sum(process_resident_memory_bytes{job="catalog-service"})
```

The baseline was collected on September 27–28, 2026 (UTC-5) while one Traffic Generator simulation continuously exercised `/api/books`.

Three observations were taken while the workload remained active. Five-minute Prometheus rate windows were used to reduce sensitivity to short-lived fluctuations.

|---|---:|---:|---:|---:|
| Target availability | 100% (2/2) | — | — | 100% |
| Throughput | 5.614 req/s | 5.607 req/s | 5.589 req/s | 5.589–5.614 req/s |
| Success rate | 100% | 100% | 100% | 100% |

| P50 latency | 25 ms | — | — | 25 ms |

## 8. Initial SLOs

The following initial objectives define the expected healthy behavior of the monitored Catalog path under approximately the baseline workload.

| SLI | Initial SLO |
|---|---:|
| Target availability before chaos | 100% of expected Catalog targets healthy |
| Request success rate | >= 99% |
| Request error rate | <= 1% |
| P95 request latency | <= 100 ms |

These objectives intentionally provide margin relative to the observed baseline rather than requiring chaos experiments to reproduce the exact baseline values.

The observed P95 was approximately 47.5 ms. The initial latency objective of 100 ms allows controlled degradation while still defining a clear healthy-state boundary.

The success-rate and error-rate objectives describe complementary views of HTTP request outcomes.

## 9. Steady-State Criteria for Chaos Experiments

Before a chaos experiment starts, the monitored path should satisfy all of the following conditions:

1. Both expected `catalog-service` replicas are discoverable and healthy in Prometheus.
2. Request success rate is at least 99%.
3. Request error rate is at most 1%.
4. P95 request latency is at most 100 ms.
5. A workload comparable to the baseline is actively reaching the service.

These criteria define the initial steady-state hypothesis for future experiments.

During and after an experiment, Hypo can compare the observed SLIs against these objectives to determine whether the system remained within the expected resilience boundaries and whether it recovered to steady state.

The project safety requirement that triggers experiment abortion when success rate falls below 50% for the configured duration is separate from the normal SLO. The 50% threshold represents a critical safety boundary, whereas the 99% success-rate objective represents normal acceptable service behavior.

## 10. Measurement Limitations

This is an initial development baseline, not a production performance benchmark.

The following limitations apply:

- The measurements were collected on a local kind cluster rather than production infrastructure.
- The baseline currently covers `catalog-service`, not every MyBookstore microservice.
- The workload represents one controlled Traffic Generator simulation and approximately 5–6 requests/s.
- CPU and memory values depend on the local execution environment and should be compared primarily within equivalent test conditions.
- HTTP latency percentiles are estimated from histogram buckets.
- The first configured latency bucket is 50 ms. Consequently, values such as P50 = 25 ms and P95 = 47.5 ms are interpolated estimates within that bucket and should not be interpreted as millisecond-precision measurements.
- The baseline contains a limited number of observations and should be refined as additional controlled experiments are executed.

## 11. Use in Later Experiments

This baseline provides the reference state for future Chaos Mesh experiments.

A typical experiment should follow this sequence:

1. Confirm the steady-state criteria.
2. Record the pre-chaos SLIs.
3. Inject a controlled failure within the configured blast radius.
4. Observe the same SLIs during the failure.
5. Abort the experiment if the safety threshold is crossed.
6. Remove or stop the fault.
7. Measure recovery.
8. Compare the resulting behavior against the SLOs and baseline.
9. Record PASS/FAIL and the observed resilience gap.

This keeps the evaluation of chaos experiments tied to measurable service behavior rather than subjective observations.
